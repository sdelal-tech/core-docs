# Core — правила разработки интерфейсов

Правила относятся только к UI. Сохраняй архитектуру, API, безопасность и инструменты проекта. Пути ниже относительны этому файлу; из корневого AGENTS.md проекта добавь ссылку на него.

## Источник

Документированная версия, дата и SHA-256 — в [манифесте](reference/source-manifest.json). Все оригинальные runtime-ассеты подключай только из **https://cdn.sdelal.tech/core/latest/**. Один `core.css`, затем штатная тема. Для мануала используй классы и штатные переменные Core без собственного CSS. Не добавляй npm-пакет Core, второй UI-фреймворк, зеркало или локальную runtime-копию.

Штатный latest/importmap.js соответствует latest. Подключай его до модулей либо используй [явную карту latest](chapters/javascript.md) или абсолютные импорты. Десять модулей — ESM; обычный script без type=module не подходит.

Latest изменяем. Для неизвестного имени или расхождения поведения прочитай текущий исходник. Временная локальная копия для анализа допустима, подмена runtime — нет. При сетевой ошибке не рисуй «похожий Core» с нуля.

## Правила CSS

1. Семантический HTML → основание Core → модификаторы → состояния. Не придумывай классы по аналогии. Регистр, двоеточия и адаптивные префиксы значимы; порядок классов в HTML не меняет каскад.
2. Сохраняй DOM-контракт: input перед label-span у checkbox/radio; прямые дети групп действий и полей; передача gap дробным flex-элементам; инициализация метрик шрифта.
3. Различай наследование и селектор потомка. `--x` и ряд рабочих переменных не наследуются; root-алиасы могут быть уже вычислены. Во вложенной сетке явно задай число колонок.
4. Для своего CSS используй узкий префикс приложения и краткую причину. Не исправляй один компонент глобальными button/input/reset. Адаптация настоящей таблицы в карточки — CSS приложения, не встроенный компонент Core.
5. Цвет фона, текста и границы — разные шкалы. `core-bg-black:500` не равен исходному чёрному. Тему Telegram без явной проверки несовместимых токенов не используй как готовую.

## Правила JS

1. EventEmitter создай до SliderManager/FormManager. StateManager — до resource либо передай через options.state. Большинство менеджеров singleton; не создавай их на каждый компонент.
2. Используй точные методы и данные из `chapters/js-*.md`. `FieldManager.registerHendler` — фактическое имя; search/date в этом модуле не реализованы.
3. `emit` — очередь с задержкой 200 мс. Async veto требует явного accept/reject. Resource dedupe не сравнивает аргументы; для смены запроса используй dedupe:false, latest:true и при необходимости abortPrevious:true. Обрабатывай отклонённые Promise.
4. Не подключай FormManager автоматически ко всем формам. Согласуй хранение публичных полей в localStorage/cookie; для временной формы используй data-form-temp. JSON POST — массив, files/multiple-select и HTTP-ошибки требуют отдельной логики. Пароли и private-поля не сохраняются локально, но входят в отправку.
5. После вставки DOM перечитай правила refresh конкретного модуля. Повторный autoInit FormManager добавляет слушатели. Destroy неодинаков: проверяй отписки, таймеры, global и singleton, не предполагай полный сброс.
6. Для PopupManager задай имя/role/aria-modal, начальный фокус и при необходимости inert фона. Не используй его hash одновременно с независимым hash-router. Не связывай пользовательский ввод напрямую с произвольными JS-выражениями.

## Приёмка

Проверь страницу с настоящим Core: 390/720/721/997/998/1200 CSS px по нужным брейкпоинтам, длинный текст, пустое/ошибочное/disabled состояния, Tab/Enter/Escape, сохранение ввода при обновлении. Проверь только заявленные темы. Для JS — повторное действие, удаление/возврат компонента, ошибки, подписки и гонки по смыслу.

Не считай загрузку CSS доказательством корректности всего UI. В ответе укажи изменённые файлы, фактические проверки, прикладные расширения и ограничения. Результаты старого отчёта не выдавай за новый прогон.
